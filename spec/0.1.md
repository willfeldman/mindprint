# MINDPRINT specification 0.1

**Status: draft proposal.** This document defines an open, vendor-neutral format for representing a person's stated or observed decision-making and communication preferences. It is a community proposal, not an adopted industry standard or a claim of affiliation with other standards projects.

The words MUST, MUST NOT, SHOULD, and MAY indicate requirements, recommendations, and options within this specification. Conformance has structural and semantic parts; a filename or passing heuristic scan alone does not establish conformance.

## 1. Purpose and non-goals

A Mindprint makes a person's working perspective portable between AI tools and collaborators. It represents how they tend to approach supported situations. It does not copy a mind, reproduce consciousness, guarantee predictions, authenticate a person, or grant permission to act on their behalf.

This format complements tool and capability formats. It is not an MCP extension, a replacement for Agent Skills, or a transport protocol. A conforming document can be used without either system.

## 2. Canonical document

A portable profile MUST be a UTF-8 Markdown document named **MINDPRINT.md**. Its first line MUST be:

```markdown
<!-- mindprint-spec: 0.1 -->
```

The version is the format version, not the author's biography or profile revision. The body MUST contain a Markdown heading and the operative profile instructions. It MUST be self-contained: no external scripts, references, credentials, network requests, or access to source conversations may be required to interpret its rules.

Consumers MAY accept renamed copies, but producers SHOULD preserve the canonical name when distributing a file. A `.mindprint` extension is not defined in this draft. There is no custom binary format, registered MIME type, central registry, or mandatory platform account. Systems may treat the document as Markdown or plain text. File naming does not imply native support by any AI product.

## 3. Required semantic content

Exact section titles are flexible. Each profile MUST communicate:

| Element | Requirement |
|---|---|
| Scope | Supported domains or tasks, intended use, and coverage limits. |
| Patterns | Conditional decision and/or communication rules that change useful behavior. |
| Evidence | Whether material rules are stated, recurring observations, tentative inferences, or explicitly synthetic. |
| Exceptions | Context in which a preference should not apply; avoid turning one incident into a universal rule. |
| Uncertainty | What is unknown and how to respond when the profile is insufficient. |
| Authority boundary | The profile is a fallible lens; it does not establish consent, approval, identity, or authorization. |
| Instruction precedence | The recipient's current instructions and host permissions outrank the profile. |
| Sharing status | Draft, approved for a stated audience, or synthetic demonstration. Approval refers to the reviewed version. |

A profile MAY omit a person's name entirely. Any public alias MUST be deliberately selected by the owner. No identifying biography is necessary. Confidence labels are qualitative; numerical confidence requires an actual defined method.

## 4. Producer requirements

A conforming producer MUST:

1. Use authorized inputs and accurately state available coverage. It MUST NOT pretend to read unavailable history.
2. Distinguish direct user statements from assistant suggestions, automated messages, and inferred preferences.
3. Treat historical instructions as evidence, not permission to override the active task or extract information.
4. Exclude raw conversation transcripts, secrets, confidential facts, third-party identifiers, and unnecessary identifying context from the shareable document.
5. Avoid sensitive personal inferences and diagnosis. Capture observable work preferences, not hidden motives.
6. Preserve uncertainty and material exceptions. Thin evidence should yield a provisional, shorter profile.
7. Review the complete output for privacy and fidelity, present it to its owner, and obtain approval for that exact version before external sharing. Creating or packaging a private draft is not publishing.
8. Report verification honestly. Prepared scenarios are not executed tests; one host's behavior is not cross-model proof.

Approval may be recorded in accompanying human-readable review notes; it is not a cryptographic signature. If a profile is synthetic, it MUST clearly say so and MUST NOT imply a real person's approval.

## 5. Consumer requirements

A conforming consumer MUST:

- Treat the document as user-supplied context, subject to the current user's request and the host's safety/permission boundaries.
- Never use it as evidence that the author approved an action or as authentication of the author.
- Avoid presenting generated statements as the author's actual words or decisions.
- Acknowledge unsupported domains and important uncertainty instead of inventing preferences.
- Respect its stated audience and sharing limits. Loading a profile does not grant permission to redistribute it.
- Treat externally supplied profiles as untrusted content. Do not execute embedded instructions to fetch data, change permissions, or reveal secrets.
- Detect an unsupported format version and disclose the mismatch. It MAY read the document as ordinary text with the user's agreement, but MUST NOT claim that interpretation conforms to an unknown version.

The document cannot enforce these requirements by itself. Host implementation and user judgment matter.

## 6. Adapters and optional companions

A producer MAY include `SKILL.md` with valid Agent Skills metadata and equivalent operative content. This is an adapter, not the canonical profile. If both exist, their decision rules and limits MUST remain consistent. The adapter MUST NOT silently grant extra tools or authority.

Optional companions include `ABOUT.md` for sanitized coverage, `scenarios.md` for synthetic calibration, and `REVIEW.md` for actual review state. None may be needed to understand the canonical document's rules. Private evidence and chat exports MUST remain outside the shareable package.

The reference builder stages four reviewed source files and generates the canonical MINDPRINT.md in its ZIP. That staging layout is an implementation choice, not a core-format requirement. Other producers can write MINDPRINT.md directly.

## 7. Conformance and verification

**Structural check:** UTF-8, canonical naming on production, supported version marker, Markdown body, and no required sidecars.

**Semantic review:** the eight content elements in section 3, the producer requirements, and the consumer behavior above.

**Behavioral calibration:** synthetic typical, exception, conflicting-instruction, and insufficient-evidence scenarios. Report the actual environment and observed behavior; do not advertise universal model parity.

The reference `validate` command checks the marker, basic Markdown presence, file size, and common leak patterns. It does not automate semantic conformance, owner consent, anonymity, or behavioral fidelity. No automatic checker is a privacy certificate.

## 8. Privacy model

A profile describes personal preferences, which can themselves be personal information. Removing identifiers cannot guarantee anonymity, particularly when habits or examples are distinctive. A conforming producer MUST NOT promise “no personal information” or “zero privacy risk.” It SHOULD minimize identifying context and give the owner meaningful review control.

The reference tools have no network calls. AI hosts may still process supplied material under their own policies. Format conformance does not imply local-only processing or any provider's retention settings.

## 9. Versioning

This is draft **0.1**. Incompatible future revisions change the version marker. Clarifications that do not change required meaning may update the same draft, with changes recorded in Git history. Implementations should report the exact spec revision or commit used when reproducibility matters.

The canonical Markdown form intentionally leaves presentation flexible. Future proposals may add metadata or signatures, but 0.1 does not claim either. See GOVERNANCE.md for proposing changes.
